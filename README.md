# doqa-ai-cases

Утилита на Python: выгружает тест-кейсы из DoQA, читает требования из папки, строит по ним
чек-лист проверок и генерирует тест-кейсы в формате, совместимом с выгрузкой DoQA.

Конвейер:

```
DoQA /api/cases/export  ──►  xlsx-выгрузка  ──►  разбор кейсов (эталоны стиля и шагов)
                                                          │
папка требований (рекурсивно)  ──►  текст + разбиение на фрагменты
                                                          │
                                        ┌─────────────────┴──────────────────┐
                                        ▼                                    ▼
                            Запрос 1: чек-лист                     Запрос 2: тест-кейсы
                            checklist.json / .md                   cases.json / .xlsx
```

На каждый фрагмент требований и каждый пакет чек-листа делается отдельный запрос к модели,
поэтому большие объёмы не упираются в контекст. Непокрытые пункты чек-листа запрашиваются
повторно, покрытие пишется в `coverage.md`.

## Установка

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

copy .env.example .env
# заполните .env: DOQA_BASE_URL, DOQA_TOKEN, OPENAI_API_KEY
```

Минимальные зависимости: `openai`, `openpyxl`, `python-docx`. Для PDF-требований нужен
`pypdf` — без него PDF-файлы пропускаются с предупреждением.

## Быстрый старт

```powershell
# полный цикл: экспорт → чек-лист → тест-кейсы
python run.py all --space-id 42 --requirements .\requirements

# только выгрузка кейсов
python run.py export --space-id 42 --out .\runs\export-sp42

# только чек-лист (DoQA не нужен)
python run.py checklist --requirements .\requirements --out .\runs\checklist

# только тест-кейсы по готовой выгрузке и готовому чек-листу
python run.py cases --requirements .\requirements ^
    --export-file .\runs\export-sp42\doqa\cases_export.xlsx ^
    --checklist-file .\runs\checklist\checklist\checklist.json
```

Полезные ключи:

| Ключ | Назначение |
| --- | --- |
| `--dry-run` | Не вызывать модель. Промпты всё равно рендерятся и сохраняются в `prompts/` |
| `--out DIR` | Каталог результатов (по умолчанию `runs/<дата-время>-space<id>`) |
| `--no-cache` | Отключить кэш ответов модели |
| `--no-prompts` | Не сохранять рендеры промптов |
| `--model` | Переопределить `OPENAI_MODEL` |
| `--version` | Показать версию |
| `-v` | Подробный лог (в файл пишется всегда) |

Фильтры экспорта соответствуют телу `/api/cases/export`: `--folder-id`, `--item-id`, `--tag-id`,
`--status`, `--priority`, `--search`, `--sort`, `--direction`, `--column`, `--format`,
а также `--filter-json '{"createdAt": {"from": "2025-01-01T00:00:00Z"}}'` для любых
полей, которых нет отдельным ключом.

`--space-id` можно не указывать, если в `.env` задан `DOQA_SPACE_ID`.

## Что получается на выходе

```
runs/20251104-215430-space42/
├─ doqa/
│  ├─ cases_export.xlsx          # исходная выгрузка
│  └─ cases.normalized.json      # разобранные кейсы (id, шаги, предусловия)
├─ checklist/
│  ├─ checklist.md               # человекочитаемый чек-лист с чекбоксами
│  └─ checklist.json             # тот же чек-лист для следующего шага
├─ cases/
│  ├─ cases.xlsx                 # тест-кейсы в структуре выгрузки DoQA
│  ├─ cases.json                 # те же кейсы + привязка к пунктам чек-листа
│  └─ coverage.md                # какие пункты остались без кейсов
├─ prompts/                      # все отправленные промпты (system + user)
├─ logs/run.log
└─ report.json                   # сводка: тайминги, токены, предупреждения
```

`cases.xlsx` повторяет колонки и их порядок из выгрузки. Если в выгрузке шаги разложены
по колонкам `Шаг 1 / Ожидаемый результат 1 / …`, утилита добавляет столько пар колонок,
сколько нужно самому длинному сгенерированному кейсу. Если шаги лежат в одной колонке
(`step` / `expectedResult`), они пишутся многострочно с нумерацией — как в выгрузке.

Новые кейсы записываются со статусом `draft`, `automationStatus = manual`, пустыми `id`
и `creator`: идентификаторы и автора присвоит DoQA при импорте.

| Переменная | По умолчанию | Описание |

| Переменная | По умолчанию | Описание |

| `REQUIREMENTS_CONTEXT_MAX_CHARS` | `18000` | Предел требований в запросе генерации |

их перекрывают.

## Промпты

Промпты лежат отдельно от кода в `prompts/` и рендерятся подстановкой `{{placeholder}}`:

| Файл | Когда используется | Плейсхолдеры |
| --- | --- | --- |
| `checklist.system.md` | Роль и правила для чек-листа | — |
| `checklist.user.md` | Один фрагмент требований | `doc_path`, `chunk_id`, `chunk_index`, `chunk_total`, `heading`, `requirements` |
| `checklist_consolidate.system.md` | Сведение чек-листа | — |
| `checklist_consolidate.user.md` | Все пункты после первичной генерации | `item_count`, `items_json` |
| `cases.system.md` | Роль и правила для тест-кейсов | — |
| `cases.user.md` | Пакет пунктов чек-листа | `requirements_context`, `checklist_items`, `reference_cases`, `library_stats`, `additional_instructions` |

Промпты можно править без изменения кода. Если шаблон не найден или в нём остался неизвестный
плейсхолдер, утилита завершится с понятной ошибкой.

Ключевые идеи промптов:

* **чек-лист** — атомарные проверки, покрытие позитивных, негативных, граничных,
  интеграционных, security- и UI-сценариев; запрет формулировок без конкретики;
* **тест-кейсы** — шаги и стиль берутся из эталонных кейсов, найденных BM25-поиском
  по выгрузке; ожидаемый результат обязателен на каждом шаге; выдумывать функциональность
  за пределами требований запрещено.

## Как выбираются эталонные кейсы

Для каждого пункта чек-листа строится запрос по его названию, проверкам и ожидаемому
результату. По выгрузке DoQA ищутся ближайшие кейсы (BM25, без внешних зависимостей),
объединяются по пакету и ограничиваются `MAX_REFERENCE_CASES`. В промпт попадают только
название, путь, приоритет, предусловия, описание и шаги — этого достаточно, чтобы
воспроизвести стиль, и мало, чтобы модель скопировала чужие данные.

## Устойчивость

* Ответы модели запрашиваются по JSON-схеме (structured outputs); если провайдер её не
  поддерживает — автоматический переход на `json_object`, затем на обычный текст с разбором.
* Невалидный JSON — один автоматический запрос на исправление.
* Ошибки сети и 5xx обрабатываются ретраями SDK; HTTP-ошибки DoQA показываются с телом ответа.
* Один битый файл требований не роняет запуск: он пропускается с предупреждением.
* Пункты чек-листа, оставшиеся без кейсов, повторно запрашиваются (`MAX_RETRY_ITEMS`),
  итоговое покрытие пишется в `coverage.md` и `report.json`.

## Ограничения

* PDF-выгрузка DoQA не разбирается: для эталонов нужен `format=xlsx`.
* Импорт готового `cases.xlsx` в DoQA утилита не выполняет — файл предназначен для
  ручной загрузки или для вашего скрипта импорта.
* При первом запуске на большом объёме требований возможны сотни запросов к модели:
  оцените `REQUIREMENTS_CHUNK_CHARS`, `CASE_BATCH_SIZE` и стоимость до запуска.
* Кэш считается по точному совпадению промпта: изменение шаблона или модели сбрасывает кэш.

## Проверка без ключей

```powershell
python tests/smoke_test.py   # весь конвейер: DoQA-заглушка + фейковая модель
python tests/llm_test.py     # LLM-клиент: JSON-режимы, ретраи, кэш, без сети
```

`smoke_test.py` поднимает локальную HTTP-заглушку DoQA, подсовывает детерминированные
ответы вместо модели и проверяет весь путь: выгрузка → разбор xlsx → чек-лист → генерация
кейсов → запись xlsx в структуре выгрузки → обратный разбор результата, а также команду
`all` через CLI.

`llm_test.py` подменяет модуль `openai` и проверяет fallback с `json_schema` на
`json_object`, отказ модели от `temperature`/`max_tokens`, исправление невалидного JSON
и работу кэша.

## Структура проекта

```
run.py                     точка входа
doqa_ai_cases/
├─ cli.py                  команды export / checklist / cases / all
├─ config.py               .env и настройки
├─ doqa_client.py          POST /api/cases/export (stdlib urllib)
├─ requirements_io.py      рекурсивное чтение md/txt/docx/pdf/xlsx/html/csv/json + чанки
├─ case_export.py          разбор и запись xlsx в формате DoQA
├─ retrieval.py            BM25-поиск похожих кейсов и фрагментов требований
├─ models.py               чек-лист, шаги, кейсы, валидация ответов
├─ schemas.py              JSON-схемы для structured outputs
├─ prompts.py              загрузка и рендер шаблонов
├─ llm.py                  OpenAI-клиент, кэш, JSON-фолбэки, --dry-run
└─ pipeline.py             оркестрация, покрытие, отчёты
prompts/                   шаблоны промптов
tests/
├─ smoke_test.py           офлайн smoke-тест конвейера и CLI
└─ llm_test.py             офлайн-тесты LLM-клиента
```
